# Transactional email — Resend as Supabase Auth's SMTP provider

Email is the one piece of personal data this app touches (rule 8: auth
necessity only). It carries exactly two messages, both generated by Supabase
Auth, never by app code:

1. **Signup confirmation** — the link that lands on `laiskelis://auth/callback`.
2. **Password reset** — `resetPasswordForEmail()`, landing on
   `laiskelis://auth/reset-password`.

There is no marketing email, no digest, no receipt. Rule 10's notifications are
push-only and do not touch this path at all.

## Why a provider is needed

Supabase's built-in sender (`noreply@mail.app.supabase.io`) is capped at a
handful of emails per hour and is documented as not for production. With 12
closed testers signing up in a burst, that cap is hit on day one and
registration silently fails for whoever is unlucky. Custom SMTP removes the
cap; Resend is the SMTP provider behind it.

Resend's free tier (3,000/month, 100/day) is far above what this app will send —
two emails per user, ever.

## The free alternative: no confirmation email at all

A domain is not the only way out, and it is worth knowing the other option
before spending money. Supabase Auth has a **Confirm email** toggle
(Authentication → Sign In / Providers → Email). Turned off, `signUp()` returns
a live session immediately and *no signup email is ever sent*. The only
remaining email is password reset — a rare, one-at-a-time action that the
built-in sender's cap comfortably survives.

What it costs:

- **A typo'd email is an unrecoverable account.** Nothing ever proves the
  address works, so the reset link is the one safety net and it silently points
  nowhere. The user's only recourse is registering again under a new nickname.
- **Signups with deliberately fake addresses become free.** For a product whose
  premise is anonymity this matters less than usual — there is no email-based
  identity to protect — but it does remove a small friction against someone
  re-registering after a ban.
- **`sign-in.tsx` needs a change.** The `awaitingConfirmation` screen
  (`app/(auth)/sign-in.tsx:124`) would never be correct, since the user is
  already signed in when `signUp()` returns. The duplicate-account detection in
  `signUpWithEmail` (`hooks/use-auth.ts:52`) also needs revisiting: the
  `identities.length === 0` trick is specific to the confirmation-on flow, and
  with confirmations off Supabase returns a plain error instead.

The domain route is recommended anyway — roughly 12 €/year against a real
recovery path and correctly-branded mail — but this is a legitimate way to ship
without one, not a hack.

## Prerequisite: a domain

Resend will only send from a domain you have proved you control. The test
sender (`onboarding@resend.dev`) delivers only to the Resend account's own
address, so it cannot serve real signups.

`laiskelis.lt` is the domain that matches the product: the bundle id
`lt.laiskelis.app` is already its reverse-DNS form. `.lt` is administered by
DOMREG (Kaunas University of Technology) and sold through accredited
registrars — Hostinger, Interneto vizija, Serveriai.lt among them, roughly
10–15 €/year. Registration is not restricted to Lithuanian residents.

DNS can stay at the registrar (four records is not a burden) or be delegated to
Cloudflare's free tier if their panel is unpleasant.

## Resend setup

1. Create the account at resend.com and add the domain.
2. **Choose the EU region (`eu-west-1`, Ireland)** when adding it. The sending
   region is fixed at creation and cannot be changed afterwards; an EU region
   keeps the mail path inside the EU, which is the right default for a
   Lithuania-only product.
3. ~~Add it as a subdomain, e.g. `mail.laiskelis.lt`, not the root.~~ Not
   how it was actually set up — `laiskelis.lt` (the apex) is the only domain
   added to Resend, and everything (auth SMTP, the manual-send function)
   sends from it directly. No subdomain exists.
4. Resend prints four DNS records. Add them at the registrar verbatim:
   - `MX` on the send subdomain → an Amazon SES feedback host (bounce handling)
   - `TXT` SPF on the send subdomain
   - `TXT` DKIM at `resend._domainkey…`
   - `TXT` DMARC at `_dmarc` (optional, `p=none` is fine to start)
   Verification usually completes in minutes; some registrars take hours.
5. Create an API key with **Sending access** only. It is shown once.

## Supabase setup

Dashboard → project `fuskxhhwkanenwmmoytu` → Authentication → Emails → SMTP
Settings. Enable custom SMTP and fill in:

| Field | Value |
| --- | --- |
| Sender email | `noreply@laiskelis.lt` (must be on the verified domain) |
| Sender name | `Laiškelis` |
| Host | `smtp.resend.com` |
| Port | `465` |
| Username | `resend` (the literal string, not an email) |
| Password | the Resend API key (`re_…`) |

Then, in Authentication → Rate Limits, raise **"Rate limit for sending
emails"**. It stays at the conservative built-in default even after custom SMTP
is enabled, and will throttle a tester cohort signing up together.

## Two things to do while in that dashboard

- **The email templates are still English Supabase defaults.** Authentication →
  Emails → Templates. Confirm signup and Reset password both need Lithuanian
  copy — they are the only user-facing strings in this product that live
  outside `lib/i18n/`, and the localization rule in `CLAUDE.md` applies to them
  in spirit even though the mechanism is different. English versions cannot be
  served conditionally here; Supabase holds one template per type, so
  Lithuanian is the right single choice.
- **Confirm the redirect allowlist** still holds `laiskelis://auth/callback`
  and `laiskelis://auth/reset-password` (see `store-release.md` §1). Changing
  the sender does not touch these, but a bounced link and an unsent email look
  identical from the outside, so rule them out together.

## Verifying

Register a throwaway account from a real build and confirm the mail arrives.
Resend's dashboard shows every send with its delivery status, which makes the
Supabase-side/Resend-side split obvious when something fails: no row in Resend
means Supabase never handed it over (SMTP credentials, rate limit); a row
marked bounced or delayed means the DNS or the recipient is the problem.

## What is deliberately not here

No transactional email beyond auth. No "your letter got likes" email, no weekly
summary, no obituary announcement — those are push, gated, and defensible as
gentle (rule 10). Adding an email channel would reopen a consent and data
question that the current design does not have to answer.
